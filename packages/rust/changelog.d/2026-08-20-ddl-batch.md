**Changed**

- **A `[[table]]`'s `ddl` is now a wide-open multi-statement SQL batch.** It runs through `execute_batch` inside one transaction, so a table can arrive with its own indexes, virtual tables and triggers — `CREATE INDEX` for B-trees, an external-content FTS5 vtab plus two triggers for keyword search with `bm25()`/`snippet()`, a `vec0` vtab plus an `embed()` trigger for stored vectors. dirsql writes user rows with plain `INSERT`/`DELETE` (an upsert is a delete and an insert in one transaction, and there is no `UPDATE` path on user rows), so those triggers stay current through the initial load and every watcher event, with no bookkeeping on dirsql's side. The two string sniffs the single-statement rule needed — `is_virtual_table_ddl` and `is_without_rowid_ddl` — are gone: what the batch produced is settled against SQLite's catalog (`pragma_table_list`) instead. A declared `name` that ends up a virtual table is a load error; one that is `WITHOUT ROWID` keeps its existing warning. (#956)

**Fixed**

- **A `ddl` holding more than one statement no longer runs only its first.** `Connection::execute` prepares one statement and discards the rest of the string, so a second statement was silently dropped — a `CREATE INDEX` that never ran, and a batch whose tail SQLite could not even parse still loading successfully. The whole batch now runs, and a statement SQLite rejects fails the load with SQLite's own message under the config entry that caused it (`table 'messages': SQLite error: near "(": syntax error`), leaving nothing behind. (#956)

- **The persistent-cache sweep now drops virtual tables before plain ones.** Drop order came from `sqlite_master`'s creation order, which happened to be safe; it is now derived from `pragma_table_list`'s type. Dropping a shadow table before the virtual table that owns it poisons the vtab's own drop even with `IF EXISTS` (probed against sqlite-vec 0.1.9), which a `ddl` batch creating a `vec0` table could now hit. (#956)
