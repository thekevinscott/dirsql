**Added**

- **The worker-call progress line splits out cache hits.** A worker may now flag a response it served from a cache of its own — `{"ok": <value>, "meta": {"cached": true}}` — and dirsql reports those separately: `dirsql: running 9204 worker calls (8811 cached)`, and `dirsql: ran 41231 worker calls in 2m41s (38104 cached)` when the query ends. A raw round-trip count reads identically whether every call ran a model or every call was a dictionary lookup, so it cannot answer the question a user watching a slow first embedding build is actually asking: will the second one cost this too. Core cannot derive the split — a cache hit *is* a round trip — so only the worker can report it, and `meta` is the generic channel for that: any `[[dirsql.function]]` may set it, and core stays ignorant of what any particular worker caches. The field is optional and advisory; a worker that omits it reports no cache hits and gets exactly the line it got before, with no `(0 cached)`. An unrecognized `meta` shape is ignored rather than failing the query. (#1034, #1001)
